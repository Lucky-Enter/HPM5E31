# 不使用 USB 的 NUC/C 仲裁方案

## 1. 前提

- C 使用 HPM5E3Y，同时运行备用 EtherCAT 主站和仲裁程序；
- A、B 已接入同一条 EtherCAT 网络；
- NUC 与 C 不能同时向 EtherCAT 网络发送周期帧；
- HPM5E3Y 只有 **1 个 ENET MAC**，该 MAC 应优先用于 C 的 EtherCAT 主站。

## 2. 方案一：独立以太网心跳（推荐）

NUC 使用第二个普通以太网接口与 C 连接，发送 UDP 心跳：

```text
NUC 普通以太网口 ── 独立网线 ── C 普通以太网口
```

NUC 每隔约 10 ms 发送一次 `HEARTBEAT`，C 连续多个周期收不到后，判定 NUC 故障并切换主站。

这条链路是管理链路，不是 EtherCAT 链路。C 的 EtherCAT ENET MAC 保持专门用于主站。

### 限制

NUC 必须有第二个网络接口。如果 NUC 只有一个网口，又不允许使用 USB 网卡，就不能采用此方案。

## 3. 方案二：监测 NUC 的 EtherCAT 周期帧（复杂，不作为首选）

C 根据 NUC 是否持续发送 EtherCAT 帧来判断 NUC 是否正常：

```text
收到周期帧       → NUC可能正常
连续超时无周期帧 → 触发切换
```

### 为什么复杂

HPM5E3Y 只有一个 ENET MAC。该 MAC 已经要用于 C 的 EtherCAT 主站，不能同时作为独立监测 MAC。因此需要增加：

```text
NUC链路 ── 100BASE-TX TAP/Monitor ── 外部PHY + MAC/MCU
                                              │
                                              └─ UART/CAN ── C
```

或者让 HPM5E3Y 的同一个 MAC 在“监测模式”和“备用主站模式”之间分时切换，这需要额外的高速切换器、TAP 和复杂的软件重初始化。

不能把普通 PHY 的 MDI 差分线直接并联到 EtherCAT 线上。必须使用带 Monitor/TAP 输出的 100BASE-TX 设备或经过验证的高阻抗接收方案。

### 方案二结论

技术上可实现，但硬件、布线和软件都比较复杂。第一版不建议采用，除非系统确实没有第二条管理通信链路。

## 4. 方案三：只监测 Link/载波/周期活动（可靠性低）

可以使用独立 PHY 的以下状态判断 NUC 是否仍有活动：

- `LINK_STATUS`；
- `CRS_DV`；
- `RX_DV`；
- 是否存在以太网载波。

### 为什么可靠性低

这些信号只能说明网口有链路或有数据活动，不能确认：

- NUC 上层控制程序是否正常；
- 发送的数据是否为有效 EtherCAT 周期帧；
- PDO 内容是否正确；
- 控制算法是否已经卡死。

例如 NUC 应用程序已经异常，但底层网卡仍保持 Link Up，仲裁器可能误判 NUC 正常。

### 方案三结论

只能作为方案一或方案二的辅助检测，不能单独作为主站切换依据。若必须单独使用，应采用较短超时并配合安全停机策略。

## 5. 三种方案比较

| 方案 | 额外硬件 | 判断能力 | 复杂度 | 建议 |
|---|---|---|---|---|
| 独立以太网 UDP 心跳 | NUC/C 各有管理网口 | 能判断 NUC 软件状态 | 低 | 推荐 |
| EtherCAT 帧监测 | TAP、监测 PHY、额外 MAC/MCU | 能判断周期帧活动 | 高 | 不作为首选 |
| Link/载波监测 | PHY 或链路检测电路 | 只能判断物理活动 | 低 | 可靠性低，仅作辅助 |

## 6. 主站切换流程

无论采用哪种检测方式，切换流程必须保持一致：

```text
检测 NUC 故障
  ↓
撤销 NUC_ACTIVE
  ↓
断开 NUC
  ↓
确认两路全断并等待
  ↓
确认 C_READY
  ↓
接通 C
  ↓
C 扫描 A、B，验证身份和 PDO
  ↓
进入 OP 并恢复控制
```

继电器/高速切换器必须支持 break-before-make，并有硬件互锁和触点反馈。C 复位或看门狗超时时，建议默认两路全断。

## 7. 最终建议

1. NUC 有第二个普通网口时，采用方案一；
2. NUC 没有第二网口时，方案二虽然可行，但实现复杂；
3. 方案三不要单独作为故障判断依据；
4. 不论采用哪种检测方式，都必须保留硬件互锁、切换间隔和安全停机流程。
